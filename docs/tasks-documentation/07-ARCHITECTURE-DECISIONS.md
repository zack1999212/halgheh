# تصمیمات معماری — ماژول Tasks

## هدف و دامنه

این سند تصمیمات معماری پیادهسازیشده در ماژول Tasks را مستند میکند. هر تصمیم شامل: زمینه، گزینههای بررسیشده، گزینه انتخابشده، دلیل، مزایا، معایب، خطرات و جایگزینهای آینده است.

نحوه خواندن برچسبها:

- **مستند به کد**: گزینهای که مستقیماً در فایل `/service/task/*`، migrations یا frontend قابل مشاهده است.
- **(بازنگری / retrospective)**: گزینهای که در کد وجود ندارد و صرفاً برای مقایسه ذکر شده است؛ نباید بهعنوان «تصمیم اتخاذشده» تلقی شود.

تم شناسههای انگلیسی (مانند `task_workspaces`، `_access_role`) عیناً از کد نقل شدهاند.

## D1 — معماری لایهای: `router` / `service` / `repository` / `models` / `schemas`

| وجه | توضیح |
|---|---|
| **زمینه** | ماژول Tasks باید بدون تغییر `service/main.py` به اپلیکیشن FastAPI موجود اضافه میشد. الگوی موجود ماژول calendar (`repository.py` با قرارداد «/commit نکند») الگوی خانه محسوب میشد. |
| **گزینهها** | (الف) قرار دادن منطق در_INLINE داخل router **(بازنگری)**؛ (ب) لایهبندی صریح router/service/repository/models/schemas **(مستند به کد: docstringهای ابتدای `router.py`، `service.py`، `repository.py`)**؛ (ج) CQRS/job جداگانه **(بازنگری)**. |
| **انتخابشده** | لایهبندی (ب). `router.py` تنها `Depends(get_db)` و کاربر احرازشده را حل میکند و به `service.py` واگذار میکند. `repository.py` فقط SQLAlchemy خالص است، خطاهای HTTP نمیدهد و commit نمیکند. |
| **دلیل** | نگهداری قوانین کسبوکار و مرز تراکنش در service، جداسازی دغدغههای HTTP از دامنه، و ایجاد یک نقطه واحد برای مجوزها (`service/task/permissions.py`). |
| **مزایا** | قابلیت تست بالا؛ تغییرات آینده ساختار تیم/Workspace تنها با تغییر `permissions.py` و scoping مخزن اعمال میشود؛ لیستها scalar-onlyاند و از N+1 بهصورت ساختاری جلوگیری میشود. |
| **معایب** | تعداد فایل و سطح بیشتر (indirection)؛ یک تغییر کوچک گاهی چند لایه را درگیر میکند. |
| **خطرات** | وابستگی دورهای: service ماژول workspace را با `import` محلی داخل توابع وارد میکند (مثلاً `_access_role`) تا از circular import جلوگیری شود؛ اگر این الگو شکسته شود، import سراسری شکست میخورد. |
| **جایگزین آینده** | در صورت رشد پیچیدگی خواندن، جداسازی مدلهای خواندن (read models) یا رویدادهای دامنه؛ انتقال predicateها به یک policy engine. |
